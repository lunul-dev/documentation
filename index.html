Introduction to Lunul Foundation & NullNet

Protocol specification · v2.4*

Lunul Foundation describes and stewards the NullNet protocol—a privacy-focused blockchain environment intended to address the trade-offs between public-ledger transparency, business confidentiality and transaction throughput.

The design described in this specification pairs a Paris-targeted EVM execution environment (Chain ID 448000) with a proposed or integrated zero-knowledge UTXO shielding component. The intended developer experience is familiar Solidity tooling alongside private transaction flows where supported.

Public blockchains can expose wallet balances, transaction relationships and contract interactions to indexers and market participants. For businesses, payroll operators, gaming platforms and treasury managers, that visibility can reveal commercially sensitive activity. NullNet’s stated objective is to give applications more control over what financial information is publicly observable.

Implementation note: this page is a styled presentation of the supplied specification. Treat performance figures and descriptions of cryptographic shielding, IP concealment, storage rent, validator penalties and integrations as project-stated claims until each is confirmed against deployed code, tests and independent review.

Cryptographic stack & dual-state architecture

EVM + UTXO model

The supplied design describes two distinct execution and state domains: an account-based EVM for contract execution, and a shielded UTXO component for confidential value transfers. These are different models and need a clearly specified bridge between them for asset accounting, proof verification and failure handling.

Execution domain A

Paris EVM account state

Solidity bytecode, contract storage, account-based balances and application logic. Public EVM state is transparent unless privacy is implemented at the application or protocol layer.

⇄
Shielding domain B

ZK-UTXO pool

Private notes or outputs, commitments and nullifiers, with proof verification intended to prevent double spending while limiting disclosure of transfer details.

Integration question: document exactly how EVM assets enter and leave the shielded pool, which contracts or relayers are trusted, what data remains public, and how supply conservation is enforced.
Wallet networking & IP privacy

The original material describes wallet providers connecting to a JSON-RPC endpoint and mentions encrypted relays intended to reduce direct exposure of client network metadata. A standard JSON-RPC connection by itself does not conceal a user's IP address from the RPC operator. IP privacy requires a separately implemented and tested transport, relay or proxy layer; it should not be described as a VPN unless it actually provides VPN-like routing and threat-model guarantees.

For production deployments, avoid exposing RPC endpoints to the public internet with permissive CORS or host settings. Restrict origins, use authenticated access where appropriate, terminate TLS at a controlled proxy, apply rate limits and avoid publishing node-management credentials.

Commitments, proofs & encrypted payloads

The supplied text references Pedersen commitments, AES-GCM payload encryption and Ed25519 signatures. These components solve different problems: commitments can hide a value while supporting verification; authenticated encryption protects message confidentiality and integrity when keys are managed correctly; signatures authenticate possession of a signing key. None alone guarantees complete transaction anonymity.

C = r · G + v · H

In this notation, v is the value being committed, r is a blinding factor, and G and H are generators in the relevant group. The curve, group encoding, generator derivation, range-proof system, key derivation and verification rules must be specified precisely. The source material mentions Curve25519 / Ed25519; do not assume a Pedersen construction is compatible with a curve or library without confirming the exact group and implementation.

03

Consensus, finality, fees & state management

Geth / Clique PoA

The source describes a customized Go-Ethereum (Geth) Clique Proof-of-Authority network using Chain ID 448000. In a PoA design, a defined set of authorized signers proposes and signs blocks. The actual trust assumptions depend on signer selection, key custody, governance, validator diversity and how the network behaves when signers fail or disagree.

State lifecycle

State rent & pruning

The source describes periodic storage charges and migration of stale state to cold snapshots. This should be treated as a proposed mechanism unless it is enforced by deployed protocol code. Pruning must preserve consensus-critical state and provide a documented recovery path.

Transaction economics

LUN gas & treasury routing

The supplied text identifies LUN as the native gas asset with 18 decimals. Fee calculation, recipient routing, treasury splits and any dynamic pricing rules should be published as explicit formulas and verified against implementation.

Finality terminology: a fast block interval is not automatically the same as irreversible finality. State the precise confirmation guarantee and failure assumptions, and publish reproducible benchmark conditions before making absolute “zero reorg” claims.

Do not copy those settings into a public production node. Keep validator keys and passwords out of shell history and process arguments; use a dedicated signer or an approved secure key-management method.
Validator security & penalties

The original material refers to automatic jailing, validator-seat revocation and slashing for double-signing or invalid proofs. These are meaningful only if the relevant enforcement logic exists in the active client and network governance rules. Publish the evidence, thresholds, appeal/recovery procedure and exact economic conditions before describing these as live protections.

Solidity compiler & EVM compatibility

Paris EVM target

The source specification states that NullNet targets the Paris EVM ruleset and warns about bytecode containing the Shanghai-era PUSH0 opcode. If the deployed client truly does not support Shanghai opcodes, contracts compiled for a newer target may fail at execution. Set the EVM target explicitly in the compiler configuration and test the exact deployed bytecode on a compatible network before production use.

Suggested build discipline: pin the Solidity compiler version, explicitly set evmVersion: "paris", lock dependency versions, reproduce builds in CI, and run deployment tests against the intended NullNet client version. The compiler version alone does not determine the EVM target.

module.exports = {

Privacy distinction: a conventional ERC-20 contract does not become shielded merely by deploying it to a privacy-oriented network. Contract state, events, balances and transfer relationships may remain public unless the network or application supplies a verified privacy mechanism for that specific asset and operation.

Developer FAQ

Quick reference
What is the NullNet Chain ID?

The supplied specification identifies Chain ID 448000. Confirm the active network configuration and RPC details from official project channels before connecting a wallet or signing transactions.

Which EVM target should contracts use?

The specification states Paris. Configure the compiler's EVM target explicitly and test deployed bytecode against the exact client version. Do not rely on compiler defaults.

Does every Solidity contract automatically get private balances?

No. EVM compatibility and transaction confidentiality are separate properties. Privacy depends on the exact protocol path, token implementation, contract design and which data is made public.

Are the performance numbers independently verified?

The provided source lists sub-400 ms finality and 100,000+ TPS. It does not include benchmark methodology or independent results, so these figures should be labelled as project-stated claims until reproducible evidence is published.

Can I expose an RPC endpoint publicly?

Only with a deliberate security design. Avoid wildcard CORS/origins, public administrative methods and unlocked validator accounts. Prefer a private bind address, authenticated proxy, TLS, rate limits, monitoring and a dedicated signing architecture.
